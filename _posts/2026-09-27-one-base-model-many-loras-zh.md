> 这是一篇 2023～2024 年的工程复盘。文中代码和架构对应当时的 vLLM 版本，请不要拿它当最新版操作手册直接复制粘贴——除非你想顺便复习一下故障排查。

## 故事要从“既要、又要、还要”说起

2023 年，大模型开始进入公司的各个核心业务。大家很快发现，通用模型虽然会聊天、会总结、偶尔还会一本正经地胡说八道，但要让它真正理解业务，光靠一段越来越长的 Prompt 并不优雅。

业务里有很多稳定且高频的东西：领域知识、任务规则、输出格式、典型处理流程。每次请求都把它们重新塞进 Prompt，就像每次上班都要重新向同事介绍公司的组织架构——理论上可行，长期看谁都受不了。

于是，各业务开始做后训练，希望把这些能力沉淀到模型参数里。但现实很快给理想递来一张 GPU 账单：

- 每个业务都做全参数微调，训练成本高；
- 每个业务都保存一套完整模型，产物巨大；
- 每个业务都部署一份基础模型，显存更是说没就没。

LoRA 正好提供了一个比较体面的解法：基础模型不动，每个业务只训练一组体积较小的低秩增量参数。

训练侧的问题暂时缓解了，推理侧却举手发言：“那我呢？”

如果一个 LoRA 仍然配一整份基础模型，训练时省下来的资源，部署时又原样花了回去。我们的目标因此变成了典型的工程“既要又要”：

- 基础模型最好只加载一份；
- 多个业务 LoRA 共用一个推理服务；
- 每个请求都能选中自己的 Adapter；
- 不同 Adapter 的请求还能一起做连续批处理；
- 省显存的同时，业务之间不能串台。

这就是我开始研究 vLLM Multi-LoRA 的原因。不是因为这个名字听起来很酷，而是因为 GPU 真的很贵。

## LoRA 的公式很短，工程问题很长

对于一个普通线性层，原始计算是：

$$
y = Wx
$$

加入 LoRA 后，基础权重 $W$ 保持不变，只增加一个低秩增量：

$$
y = Wx + sBAx
$$

$A$ 负责把输入降到低维空间，$B$ 再把它映射回来，$s$ 是缩放系数。公式看起来十分友好，甚至让人产生“这不就是多做两次矩阵乘法吗”的错觉。

如果同一个服务里有多个 Adapter，而且一个 batch 里的不同请求还可能选择不同 Adapter，公式就变成：

$$
y_i = Wx_i + s_{k_i}B_{k_i}A_{k_i}x_i
$$

只多了一个下标 $k_i$，工程复杂度却突然开始自由生长。这个下标背后包含：

- Adapter 权重怎么加载和管理；
- 每个请求应该选哪个 Adapter；
- 连续批处理后，每个 token 又该选哪个 Adapter；
- 张量并行下 A、B 怎么切；
- 不同模型的层名和结构怎么映射；
- Adapter 如果带扩展 token，词表边界怎么处理。

所以，LoRA 的数学部分像一张便利贴，Multi-LoRA 的系统实现更像一块白板，而且很快会写满。

## 第一回合：自己动手实现 Multi-LoRA

当时官方方案还不成熟，业务又不能坐在旁边等框架长大，于是第一阶段选择了手工打通整条链路。

### 先把多组 A/B 矩阵码整齐

单个 Adapter 只有一组 $A$ 和 $B$。为了让多组 Adapter 同时驻留，可以沿着 Adapter 维度把权重堆叠起来：

```text
lora_A: [num_loras, rank, input_dim]
lora_B: [num_loras, output_dim, rank]
```

基础层照常计算 $Wx$，然后根据当前 token 对应的 Adapter 索引，选择正确的 $A_k$ 和 $B_k$，计算增量后加回输出：

```python
base_output = base_linear(x)
lora_output = dispatch_and_apply_lora(
    x,
    lora_a_stacked,
    lora_b_stacked,
    adapter_indices,
)
output = base_output + lora_output
```

写到这里，一切看起来都很顺利。通常这也是工程故事即将进入主线冲突的信号。

### 真正难的不是乘法，而是别把人送错房间

vLLM 使用连续批处理。一个物理 batch 中可能混着多个请求：A 业务用 Adapter 1，B 业务用 Adapter 2，还有一个请求坚持使用原始基础模型。

因此，不能对整个 batch 统一套用一组 LoRA 权重。系统必须在调度阶段保留请求与 Adapter 的关系，再把它展开成 token 级映射，最后交给 LoRA kernel。

这里最麻烦的 bug 往往不是程序崩溃，而是程序不崩。映射一旦偏移，token 可能悄悄用了别人的 Adapter。输出依然语句通顺，日志也岁月静好，只是业务能力已经串台。

这类错误像外卖送错门：餐盒完整、骑手准时、系统显示已送达，但你打开一看，自己的减脂餐变成了隔壁的炸鸡。

所以我逐渐意识到，Multi-LoRA 并不是某个模型层的小功能。它从请求入口一路穿过调度、批处理、模型执行和 kernel，是一条完整的系统链路。

### 张量并行：线性层也有很多种性格

在 vLLM 中，不是所有线性层都等同于 `torch.nn.Linear`。进入张量并行世界后，至少会遇到：

- Column Parallel Linear；
- Row Parallel Linear；
- QKV Packed Linear；
- Merged Column Parallel Linear。

不同层的权重切分方向不同，LoRA A/B 的切分方式和聚合位置也会变化。

比如 QKV 在模型内部常被打包为一次线性计算，但 Adapter 文件里可能仍然分别保存 `q_proj`、`k_proj`、`v_proj`。加载时不仅要认出这三位其实住在同一个 packed layer 里，还要保证顺序、宽度和张量并行切分全部一致。

MLP 也有同类问题。模型可能把 gate 和 up projection 合并计算，Adapter 却仍以两个独立模块保存。系统需要建立明确映射，不能指望它们在运行时凭缘分相认。

### 从“跑起来了”到“业务真的在用”

第一阶段的实现最终进入了实际推理服务，开始承载业务 LoRA 请求。

上线很重要，因为概念验证只需要回答“能不能跑”，线上系统还要回答更多问题：

- 请求与 Adapter 是否始终对应正确；
- 多业务共享底模时是否相互隔离；
- 服务能否在有限资源下稳定运行；
- 新业务接入时是否必须再复制一套基础模型。

这套方案让训练阶段通过 LoRA 得到的资源优势延续到了推理阶段，也证明了“共享基础模型、按请求路由 Adapter”在真实业务里可行。

不过，工程系统一旦上线，就会开始诚实地展示它所有的脾气：

- LoRA rank 和槽位数量有硬编码；
- Adapter 的加载、激活、卸载和淘汰需要自己维护；
- 模型实现与 LoRA 逻辑耦合较深；
- Embedding、LM Head 和 Sampler 没有形成统一设计；
- vLLM 上游一更新，迁移工作就像一次开卷考试，只是书也换版了。

这些问题不意味着第一阶段失败。相反，只有系统真的服务过业务，抽象的“维护成本”才会变成具体的问题清单。

## 第二回合：接入官方 Multi-LoRA，轮到 Qwen 做适配

随着 vLLM 官方 Multi-LoRA 框架逐渐成形，工作重点从“整套都自己做”变成了“让 Qwen 正确接入官方机制”。

官方框架把职责拆得更清楚：

- `LoRAConfig` 管理最大 rank、Adapter 数量和扩展词表等配置；
- Model Manager 负责 Adapter 注册、激活、移除和槽位管理；
- Layer Wrapper 封装不同类型的张量并行层；
- Mapping 负责把请求或 token 路由到正确的 Adapter；
- 模型只需要描述自己的结构差异和模块映射。

这是一种令人舒适的变化：通用问题交给框架，模型适配层不再兼职成为一套迷你基础设施。

2024 年 1 月，我完成了 Qwen 的 LoRA 适配，相关修改形成了 `Add qwen-lora support` 提交。代码量比第一阶段少了，但需要确认的语义边界一点也不少。

## Qwen 适配里的几个“小问题”

工程师说“小问题”时，通常只是表示它还没有大到需要开事故复盘会。

### 1. `supports_lora` 只是入场券

框架首先需要知道模型是否支持 LoRA，所以 Qwen 要显式声明能力，并在构造过程中接收 `LoRAConfig`。

但加一个开关不等于适配完成。LoRA 配置可能影响模型初始化，尤其是 Embedding 和 LM Head 的尺寸。真正的适配工作才刚开始。

### 2. 同一种功能，大家偏偏不叫同一个名字

官方框架常见的 MLP 映射是：

```text
gate_proj + up_proj -> gate_up_proj
```

而当时 Qwen 使用的是：

```text
w2 + w1 -> gate_up_proj
```

名字对不上，Adapter 权重就找不到目标层。于是需要把 Qwen 的模块命名翻译成框架能够理解的 packed-module 关系。

此外还有 `c_proj`、`c_attn` 等名字。仅仅把某个后缀塞进目标列表并不安全，因为同名模块可能出现在模型的不同位置，底层类型、维度和可包装能力也可能不同。

### 3. 名字对上了，不代表它真的能穿这件外套

Model Manager 通常先按名称寻找目标模块，然后使用 LoRA wrapper 替换原始层。但名称匹配只是第一关，目标对象还必须属于框架支持的层类型。

如果一个模块被名字规则命中，却无法转换成 `BaseLayerWithLoRA`，还硬把它注册进 Manager，后续设置权重和更新映射时就会访问根本不存在的 LoRA 属性。

更稳妥的处理是：

```python
new_module = from_layer(module)
if new_module is None:
    continue
register_lora_module(new_module)
```

不知道怎么处理的层，要么明确跳过并记录，要么直接报错。让原始层假装自己支持 LoRA，属于“先混进群聊再说”，后面通常没有好事。

### 4. 扩展词表不是把 Embedding 拉长就结束了

有些 Adapter 会附带新增 token。最初很容易认为：把输入 Embedding 扩大一点，不就行了吗？

不完全行。生成模型的词表边界至少同时影响：

1. 输入 Embedding；
2. 输出 LM Head；
3. Sampler 的有效采样范围。

基础词表、每个 Adapter 的扩展词表，以及为了 kernel 对齐加入的 padding，还是三个不同概念。

假设基础词表大小为 $V$，每个 Adapter 最多增加 $E$ 个 token，同时容纳 $N$ 个 Adapter，那么 Embedding 的物理容量可能需要达到：

$$
V + N \times E
$$

但这不意味着某个请求可以采样所有 Adapter 的扩展 token。Sampler 必须知道当前 Adapter 的有效边界，否则 A 业务可能生成 B 业务的专属 token——这次不只是外卖送错门，而是连菜单都串了。

因此，Embedding、LM Head 和 Sampler 必须作为一个整体设计。

### 5. Packed LoRA 最怕“形状都对，顺序错了”

Packed layer 可以减少 kernel launch，提高执行效率，但它要求权重顺序与模型计算严格一致。

假设模型内部顺序是 `w2, w1`，Adapter 加载时却按 `w1, w2` 写入。所有 tensor shape 都可能完全正确，程序也能顺利运行，但两组 LoRA 增量会落到错误的输出 slice 上。

这种 bug 最能教育人：shape 对得上，只能证明张量能放进去，不能证明放对了地方。工程正确性还需要模块语义、权重顺序和执行切片同时一致。

## 两个阶段，到底差在哪儿

| 维度 | 手工实现阶段 | 官方 Multi-LoRA 阶段 |
|---|---|---|
| 核心目标 | 尽快打通并上线业务 | 把 Qwen 接入统一框架 |
| 权重管理 | 自己维护 A/B 堆叠 | Model Manager 统一管理 |
| 请求路由 | 自己维护 token 索引 | 使用框架 Mapping |
| 模型耦合 | LoRA 逻辑深入模型代码 | 模型主要声明能力和映射 |
| 张量并行 | 各类层逐个处理 | 复用官方 Layer Wrapper |
| 扩展词表 | 支持不够完整 | 联动 Embedding、LM Head、Sampler |
| 生命周期 | 加载卸载都要自己操心 | 由框架统一管理 |
| 长期维护 | 能解决阶段性业务问题 | 更容易跟随上游演进 |

第二阶段的代码更少，不是问题凭空消失了，而是通用问题被放回了正确的抽象层。

## 这段经历留下的几条经验

### 公式越简单，越不要低估它进入系统后的社交关系

`BAx` 本身不复杂。复杂的是它要同时和连续批处理、动态调度、张量并行、模型异构、权重生命周期以及词表管理相处。

一个功能进入生产系统后，难点经常不在功能本身，而在它和所有既有能力的组合。

### 自己走过底层，才能真正看懂上层抽象

第一阶段的手工实现不是最终架构，却让我直接处理过 A/B 堆叠、token 路由和并行层切分。后来阅读官方设计时，很多抽象不再只是类名，而是能对应到具体问题。

踩坑不能自动让人进步，但把坑画进地图里可以。

### 模型适配远不止打开一个开关

真正需要确认的是：

- Adapter 模块名如何对应模型模块；
- packed layer 的权重怎样组合；
- 哪些层可以被 LoRA wrapper 替换；
- 输入和输出词表是否需要扩展；
- Sampler 是否理解有效词表边界；
- 张量并行下各个维度如何切分。

`supports_lora = True` 更像一句自我介绍，不是毕业证书。

### 对无法证明正确的路径，宁可保持显式

Multi-LoRA 中，静默兼容往往比直接报错危险。未知模块类型、无法解释的 Adapter 权重、不一致的 packed mapping，都应该被明确跳过、记录或拒绝。

报错至少会叫你来处理；错误结果却可能穿着正常输出的外套悄悄上线。

### 历史代码不只记录答案，也记录当时为什么这么答

回看早期代码，硬编码、临时日志和未完成实验都很明显。但它们也保存了问题被发现、方案被调整的过程。

技术复盘如果只展示最终的优雅架构，就像旅游攻略只放山顶照片：风景很好，但看不出中间到底爬了多少台阶。

## 最后

这次探索始于一个朴素愿望：让同一个 vLLM 服务加载多组 Qwen LoRA，大家共享一份基础模型，不要每个业务都单独占一套 GPU 资源。

第一阶段，我从 A/B 权重堆叠、token 路由和张量并行层开始，手工实现 Multi-LoRA 并部署到实际业务；第二阶段，我转向官方架构，完成 Qwen 的模块映射、层包装和扩展词表适配。

如果用一句话总结这段经历，大概是：

> Multi-LoRA 的难点不是多做两次矩阵乘法，而是让正确的 Adapter，在正确的时间，以正确的并行方式，找到正确的 token 和正确的模型层——全程还不能走错片场。

公式只是故事的开头。真正决定它能否上线的，永远是后面那一长串系统细节。
